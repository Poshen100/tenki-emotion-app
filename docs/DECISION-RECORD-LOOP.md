## 0. 🔴 根因：一個常數服務了兩個需求相反的方向

founder 2026-10-09：「我依照計劃進場完成，但是後面這一段就沒有記錄到。」

唯一能把人帶回去填結果的那條路是 `acceptReturnTicket()`
（`apps/preview/decision-alert.js:1121`），而它檢查：

```js
if (typeof t.at !== 'number' || Date.now() - t.at > HANDOFF_TTL_MS) return false;
//                                                 ^^^^^^^^^^^^^^^ = 5 * 60 * 1000
```

**五分鐘。** founder 那天等了快一個小時 —— 回程票在他回來之前就作廢了。
**不是他忘了記，是接他的那班車已經開走了。**

而這個常數**本來是對的** —— 只是對另一個方向。它的註解自己寫著理由：

> 「信物的保鮮期。過期就不自動起跑 —— 昨天的快訊今天不該自己開始一個決策。」

那句話對**出去**（快訊 → 開始決策）完全正確。問題是**回來**沿用了同一個常數：

| 方向 | 需要的壽命 | 理由 |
|---|---|---|
| 出去：快訊 → 開始一個決策 | **短**（5 分鐘合理） | 昨天的快訊不該今天自己起跑 |
| 回來：下完單 → 填結果 | **跟著那筆紀錄活著** | 它在等你，而**等待沒有時間表** |

一個常數服務兩個需求相反的方向，其中一個必然是錯的。
而錯的那個方向，正好就是這個產品的主動線。

> 📌 提煉成規則（已進 `docs/PLAYBOOK.md`）：
> **一個常數被兩條路徑共用時，先問這兩條路徑要的是不是同一件事。**
> 共用常數的誘因很強（少一個名字、少一處要維護），而它的代價是
> 「其中一邊永遠是錯的，而且錯得沒有症狀」—— 回程票作廢不會報錯，
> 只會安靜地不開。

## 1. 🔴 先修正那個計時器的心智模型

founder 的原始想像（2026-10-11 原話）：

> 「決策計時器⏱️ 會在我作決定（做完交易後）時間到，可以記錄各種狀態
> 花了多久時間才決定，最後是贏還輸」

**這個模型比當初做出來的那個好。** 當初那個只量到「按鈕與按鈕之間」
（已於 2026-10-11 把它的平均值退場，見 `docs/VISUAL-DIRECTION.md`）。
founder 想要的是跨越整段的時間 —— 那是對的。

### 1.1 一件要往回推的事：「時間到」

**不要倒數。** 三個理由，每一個單獨都足夠：

1. **App 不知道交易什麼時候結束。** 要知道就得接券商，而「不做一鍵跳進
   交易 App 的捷徑」是已立的規則 —— 接券商比那個更深。
2. `docs/PLAYBOOK.md` 已記著「跑了 14 小時的計時器」那道傷：
   跨越數小時的 running timer 在 iOS 上會被殺、重載、時鐘倒退。
3. **一個在持倉中間響的倒數，只有兩種下場**：它是錯的（交易沒有已知時長），
   或者它變成「該出場了吧」的壓力。後者正是 `TRADING-METHODOLOGY.md` §6
   拆掉計時器的原因 —— 用時間當紀律指標「對品質最好的 setup 罰得最重」。

### 1.2 改成四個時間戳、三段時長

把「一個計時器」換成「一筆紀錄的生命週期」。**每一個都可以是 null。**

```
  alertAt ──────► judgedAt ──────► enteredAt ──────► closedAt
          審視               等待               持有          + tradeResult
     （快訊到我判定）    （我判定到真的進場）  （進場到出場）
```

| 欄位 | 誰寫 | 缺的時候 |
|---|---|---|
| `alertAt` | 快訊到達 / 掃描完成 | 手動開的決策沒有這一欄 |
| `judgedAt` | 按下「進場」或「先不動」 | = 既有的收束時刻 |
| `enteredAt` | **使用者自己說「我進場了」**（§3） | `null` ＝ 不知道他何時進場 |
| `closedAt` | 填結果的那一刻 **或** 使用者挑的時間 | `null` ＝ 還在等 |

三段時長**全部是推導的**，不另存：`審視 = judgedAt − alertAt` 等等。
任一端是 null → 那一段就是 null → 畫面上那一格印「—」。

> 🔴 這是 2026-10-10／10-11 兩刀反覆打下的那條規則：**缺就是缺，回 `null`**。
> 把 `enteredAt` 填一個「大概是判定後 10 分鐘吧」的預設值，下游**分不出來**，
> 而「等待 10 分鐘」會變成一句它不知道的事實。
>
> 🔴 **三段時長只以「每一筆的事實」出現，不得彙總成分數。**
> 2026-10-11 剛把「平均用時」整格退場，理由同一條。
> 要做分布（而不是平均）得 founder 另外拍板。

### 1.3「最後是贏還輸」

契約已經有了（`domain/src/contracts/trade-result.ts`，§9b），
而且**畫面上不准用自然的交易詞彙** —— `PROHIBITED_VOCABULARY_ZH` 擋掉
獲利／虧損／停損／停利。既有的三顆晶片是跑過 `findProhibitedTerms` 的：

| 內部值 | 畫面上 |
|---|---|
| `profit_taken` | 達到目標 |
| `stopped_out` | 觸及保護價 |
| `scratch` | 打平出場 |

**一律沿用這三顆，不要另造。** 第四個狀態（`pending`）是「未選取」，
刻意沒有晶片 —— 多一顆可切換的會讓「取消選取」變成兩個意思。

## 2. 🔴 補填 ≠ 補記 —— 兩件事，成本差八倍

這是整份規格最重要的區分。搞混它，所有提醒都會變成家事。

| | 補填結果 | 補記一筆 |
|---|---|---|
| **情形** | 紀錄在，只缺 `tradeResult` | 整筆完全沒記（App 外發生的） |
| **使用者要做的** | **點一下** | 填一張表（日期／標的／模板／判定） |
| **UI** | 三顆晶片 | `openBackfill()` 表單（2026-10-10 已做） |
| **誰導向它** | **所有提醒** | 使用者自己從 Session 頁進去 |

🔴 **所有提醒的終點都是「補填」，不是「補記」。**
把提醒導到那張表單，等於把一下的事變成八下 —— 而使用者會的反應是不再點它。

判準走 `window.TENKI_OUTCOME.awaitsResult(rec)`（共用模組）。
那支模組的註解早就預留了這件事：

> 「Session 列表、Session 詳情、**未來任何想提醒的面**都要用同一個判準。」

## 3. 誰寫 `enteredAt`？—— 不要猜，問一句就好

founder 的動線是「判定 → 跳到交易 App 下單 → 回來」。
`judgedAt` 跟真正進場之間可以隔一小時（他那天就是）。

**收束頁多一個狀態，不是多一個問題。** 按下「進場」之後，收束頁的那顆
主位按鈕從「查看決策紀錄」旁邊多一顆**「我下單了」**：

- 按了 → `enteredAt = Date.now()`，紀錄進入「持倉中」
- 沒按 → `enteredAt` 永遠是 `null`，等待那一段就是「—」。**不猜。**

🔴 **它不是必填，也不催。** 沒按的人只是少一段時長，
結果照樣填得到（`closedAt` 不依賴 `enteredAt`）。
🔴 **不得在這裡放任何「要不要幫你開交易 App」** —— 已立的規則。

## 4. 🔴 智能提醒：三層，而且每一層都比下一層便宜

設計原則（違反任一條就不是「智能」而是催繳）：

1. **只在它確知有東西沒記的時候提醒** —— `awaitsResult()` 是確定的，零猜測。
2. **時機跟「那件事已經結束了」對齊，不跟時鐘對齊。** 固定「兩小時後問」是笨的。
3. **一次只問一個問題，而且一根手指答得完。**
4. **絕不倒數、不記連續天數、不扣分。** 沒填的紀錄**不是壞紀錄**。
5. **問不到就不問了。** 永不放棄的提醒會變成噪音。

### L0 — 不提醒，只是看得見（✅ 2026-10-09 已做）

Session 列表上那一行「結果還沒填 · 點進去補上」。**打擾成本 0。**
下一次打開 App 就看到。

### L1 — 下一則快訊順手帶（🚧 founder 的主意，而且它最好）

> founder 原話：「之後可能跳快訊可以補記錄」

快訊面板**最上面一條細帶**：

```
┌─────────────────────────────────────────┐
│ 上一筆 ES1! 還沒填結果                  │
│ [達到目標] [觸及保護價] [打平出場]      │
└─────────────────────────────────────────┘
      ↓ 下面是這一則新快訊，完全不受影響
```

**為什麼這一層是最好的那一層：**

- 它搭的是一個**你已經同意被打擾**的時刻 → **額外打擾成本 0**
- 情境對：快訊進來的時候你正在交易腦袋裡，答案就在手邊
- 不是 modal，是一條帶 —— 它不奪取任何東西
- 🔴 **零新基礎設施**：推播是現成的、面板是現成的、晶片是現成的。
  L2 要排程器，L1 一行後端都不用動。

**硬規則：**

| 規則 | 為什麼 |
|---|---|
| 不得阻擋、不得搶焦點 | 這一頁的工作是**新的那個決策**，補填是順便 |
| 忽略它 → 新快訊的流程逐步不變 | 一條帶子不該改變主動線的任何一步 |
| 一條帶最多講**一筆** | 多筆就講「還有 N 筆」並連到 Session 頁；
  一條帶上三組晶片是一張表單假裝自己是帶子 |
| 填完 → 帶子收起，**不跳頁** | 跳頁會把他從新快訊上扯走 |
| 不得用倒數、不得用紅色 | 它是一句事實，不是一個逾期通知 |

### L2 — 盤後一則推播（🚧 需要新基礎設施）

ET 收盤之後，如果今天有 open record：**「今天有 1 筆還沒填結果」**，
點進去直接到那三顆晶片。

**為什麼是收盤後**：因為**答案在這一刻才存在**。盤中問是在問一件還沒發生的事；
隔天問，他已經想不起來那天的細節（founder 那四筆就是隔天補的）。

**每天最多一則。連續 3 天沒反應就停**（§4 原則 5）。

🔴 **這一層落地之前有三個洞要補，每一個都會讓它安靜地失效：**

1. **`tag: 'tenki-alert'` 是單一標籤**（`apps/preview/sw.js:20`）。
   提醒用同一個 tag → **它會把一則真正的快訊蓋掉**。提醒要自己的 tag。
2. **`notificationclick` 不理 `data.url`**（`sw.js:27`）：它掃視窗，
   只要有一個 URL 含 `/decision-alert/` 就 `focus()` 並 return ——
   **深連結被吞掉**，使用者點了提醒卻停在原來那一頁，看起來像壞了。
3. **iOS 的 Web Push 只在主畫面 App 裡存在**（PLAYBOOK 已記）。
   所以**推播不能是唯一的路** —— L0/L1 必須自己站得住。

### L3 — 沒有 L3

不追、不 email、不連續紀錄、不成就、不扣分。

🔴 **三層就是上限，這是設計的一部分，不是還沒做完。**
這個產品的立場是「看了沒做也是一個決定」—— 一個會一直催你填表的 App，
教的是相反的東西。

## 5. 回程票：壽命改成跟著那筆紀錄

§0 的修法。**不是把 5 分鐘改成 2 小時**（那只是把同一個錯猜大一點），
而是把 TTL 換成一個**它自己就對**的條件：

```
票有效  ⇔  那筆紀錄還在等結果（awaitsResult(rec)）
```

紀錄被填上結果，就是票的過期 —— **過期由那件事本身定義，不由時鐘定義。**

- 出去那個方向（`HANDOFF_KEY`）**維持 5 分鐘**，它的理由仍然成立。
  兩個方向從此是兩個具名常數，而不是一個。
- ⚠️ `alreadyPersisted` / `recordTs` 的語意**一個字都不能動** ——
  那是在擋「同一筆決策存兩份」，而統計會因此失真。
- ⚠️ 票裡的 `ts` 找不到對應紀錄時仍然 return false（紀錄被清掉的情形）。
